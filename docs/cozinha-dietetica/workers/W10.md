## 2. Contexto e invariantes funcionais (não reabrir decisões)

O módulo é exclusivo para Organização Militar Hospitalar, inicialmente o HGeSM; banco separado do financeiro/logístico e da extensão Empresas. O projeto Firebase hospitalar já foi criado pelo usuário com **Project ID \`cozinha-dietetica\`**, Firestore **\`(default)\`**, Auth e-mail/senha, aplicativo web e **Rules fechadas** \`allow read, write: if false;\`. O próprio projeto real não é ambiente autorizado para inserir dados clínicos ou ser usado como QA sem credenciais/autorizações específicas. **Não alterar Rules**, não habilitar escrita direta do cliente, não criar usuários/coleções no console ou dados reais, não baixar JSON de service account.

Médico prescreve, unidade registra a dieta vigente conforme prescrição, e **envia mapas manualmente**. Nutrição **audita**, sem homologar rotineiramente pedidos. A cozinha recebe, produz, confere, expede e distribui; entrega só existe com confirmação válida. Planejamento alimentar automático é futuro e opcional.

Três ciclos locais, fuso \`America/Sao_Paulo\`:
- 06h: café da manhã + lanche da manhã; fechamento/envio regular até **06:00**, tolerância de entrega da principal até **06:30**; mapa pode ser confeccionado na véspera.
- 10h: almoço + lanche da tarde; prazo **10:00**, tolerância **10:30**.
- 16h: jantar + ceia; prazo **16:00**, tolerância **16:30**.

**Tolerância não amplia prazo regular de envio.** Após tolerância, a rotina prevê secundária; exceção clínica tem alerta/escalonamento humano, jamais abandono alimentar automático. Alta/transferência apenas **prevista** não cancela refeição. Transferência confirmada não duplica pedido. Jejum, alergia crítica e alteração de prescrição após preparo bloqueiam liberação incompatível. Não atribuir culpa administrativa por algoritmo.
